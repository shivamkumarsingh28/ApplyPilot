# ApplyPilot Frontend — Complete Code Document

This is the **only document file created for the `frontend/` folder**, as requested. It is not called README.
Read it top to bottom and you will understand **every folder, every file, and every important line of code**:
how pages are structured, how the theme (dark/light) works, how the chatbot UI talks to the backend,
and exactly where to add future features.

> **Stack in one line:** Next.js 16 (App Router) + React 19 + TypeScript, no UI library — one CSS
> file (`app/globals.css`) driven by CSS variables, so dark/light theming is a variable swap, not
> a component rewrite. No state library: each page owns its state with React hooks and talks to the
> backend through one fetch wrapper (`lib/api.ts`).

## 1. The one idea behind the frontend

Three conventions explain almost everything:

1. **Every page is a client component behind an `AuthGate`.** Pages start with `"use client"`,
   keep state in `useState`, load data in `useEffect`, and render through shared `Card`/`Badge`
   primitives. `AuthGate` guarantees a token exists (else redirect to `/login`) and renders the
   nav + container, so a page file contains only its own screen's logic.
2. **All backend access goes through `lib/api.ts`.** No page calls `fetch` directly (except the
   blob helper inside `api.ts` itself). The wrapper adds the Bearer token, parses error `detail`s
   into thrown `Error`s, and force-logs-out on 401. Pages therefore write
   `api.get<Notice[]>("/notices")` and `catch (e) => setError(e.message)`.
3. **Types mirror the backend schemas.** `lib/types.ts` hand-mirrors the backend's Pydantic
   response models (§4.3). When you change a backend response, change the type here in the same
   commit — TypeScript then finds every page that needs updating at build time.

Styling follows the same centralisation: components use semantic class names (`.card`, `.badge`,
`.msg`) defined once in `globals.css`; colours are **never** hard-coded in components — they use
`var(--…)`, which is what makes the dark theme a pure variable override (§5).

## 3. How a page loads (life of a screen)

Example: opening `/assistant` while signed in.

```
1. layout.tsx renders <html data-theme="…"> — the inline script sets the theme attribute
   BEFORE first paint (from localStorage, else system preference), so there is no flash.
2. The page component mounts inside AuthGate: no token in localStorage → router.replace("/login");
   with a token → Nav + <main class="container"> render.
3. The page's useEffect fires its API calls (api.get/post via lib/api.ts, Bearer attached).
4. Responses land in useState; React re-renders; loading states are simple conditionals
   (e.g. {!ready ? "Loading..." : …} on the notice page).
5. Any 401 mid-session: api.ts clears the token and hard-redirects to /login.
6. Errors: pages catch, store e.message in an `error` state, show <ErrorText>.
```

The token lives in `localStorage` under `applypilot_token` (see `auth` in `lib/api.ts`) — set at
login/register, set by the backend's OAuth callback page, cleared on sign-out/401.

Line numbers refer to the files as they are today. Trivial lines are grouped.

### 4.1 Root

**`app/layout.tsx`** (18 lines) — the HTML shell for every page:

| Lines | What and why |
|---|---|
| L1-3 | Imports `Metadata` type + the global stylesheet (imported once here, applies everywhere). |
| L5-8 | Page metadata: title "ApplyPilot" + description (browser tab, search/social previews). |
| L10 | `themeScript` — a tiny inline script string: read `applypilot_theme` from localStorage; if unset/invalid use `matchMedia("(prefers-color-scheme: dark)")`; set `document.documentElement.dataset.theme`. |
| L12-17 | `RootLayout`: `<html lang="en" suppressHydrationWarning>` (the attribute is needed precisely because the inline script mutates `<html>` before React hydrates — without it React would warn), `<head>` injects the script via `dangerouslySetInnerHTML` (the standard Next way to run code pre-paint), `<body>{children}</body>`. |

**`app/globals.css`** (78 lines) — the entire design system. Structure top→bottom:

| Section | What and why |
|---|---|
| `:root` tokens | Light theme variables: `--bg` (+ a two-stop radial `--bg-grad` backdrop), `--card/--card2` surfaces, `--ink/--muted` text, `--line` borders, `--brand/--brand2` (blue→violet gradient pair), semantic `--good/--warn/--bad`, `--input`, `--shadow`, `--me` (my chat bubble). Every colour in the app resolves to one of these. |
| `:root[data-theme="dark"]` | The **same variables, dark values** (deep navy bg, lighter ink, brighter brand). Nothing else in the file mentions dark — components can't tell which theme is active. This single block is the whole dark mode. |
| Base | `body` uses the bg vars + fixed gradient backdrop + a colour transition (theme switches animate); links; `.container` (1020px centre column + a `rise` entrance animation). |
| Nav | Sticky, translucent (`color-mix` + `backdrop-filter` blur), pill links; the active link is a brand-gradient pill (not an underline) so the current page is obvious; `.theme-toggle` is a neutral chip button. |
| Cards/type | `.card` (16px radius, border, token shadow), headings, `.grid` (auto-fit ≥280px columns), muted/small text, error/ok colours. |
| Forms | Full-width inputs on `--input` bg (theme-correct), visible `:focus-visible` outlines in brand colour on **all** interactive elements (keyboard accessibility), buttons as brand gradients with hover lift, `.secondary/.danger/.link/.chip` variants, `.row` flex form rows. |
| Tables/badges/bars | Token borders; badges tint via `color-mix(in srgb, var(--good) 15%, var(--card))` so they adapt to both themes automatically; progress `.bar` with gradient fill + width transition. |
| Chat | `.chat` scroll region (max-height 58vh, smooth scroll), `.chat-row` (+`.me` right-aligned), gradient `.avatar`, `.msg` bubbles (82% max width, asymmetric corner radii — flattened on the avatar side), `.msg-meta` (timestamp + badges row), `.typing` three-dot blink animation (dots are `<i>` elements), `.chips` suggestion row, `.composer` (input row pinned under a top border). |
| Misc | `.preview` checkerboard backdrop for transparent-ish image previews, `.login` centred narrow card, `.progress` text. |
| Media queries | ≤640px: bubbles widen to 92%, smaller h1. `prefers-reduced-motion`: all animations/transitions disabled — an accessibility requirement, not a nicety. |

**`components/ThemeToggle.tsx`** (33 lines) — the toggle + helpers:

| Lines | What and why |
|---|---|
| L1-3 | `"use client"` (uses state/effects/localStorage), React imports, `Theme` type. |
| L6-9 | `applyTheme(t)`: sets `documentElement.dataset.theme` (the CSS switch) and persists to localStorage, both failure-tolerant (`try/catch` — private mode can block storage). |
| L11-17 | `initialTheme()`: saved choice wins; else the OS preference; defaults light. Mirrors the layout inline script (script = pre-paint, this = post-mount source of truth). |
| L19-33 | The component: starts as `"light"`, corrects itself in `useEffect` from `initialTheme()` (server HTML can't know the theme — hence the two-step), renders a button showing the *target* mode ("🌙 Dark" while in light, "☀️ Light" while in dark) with `aria-label`/`aria-pressed`/`title` for assistive tech, and toggles on click. |

### 4.2 Shell components

**`components/AuthGate.tsx`** (22 lines) — wraps every signed-in page: on mount, no token →
`router.replace("/login")` (replace, so Back doesn't loop); token → set `ready`. Renders `null`
until ready (prevents a flash of protected UI), then `<Nav/>` + `<main className="container">`.
The login page deliberately does **not** use AuthGate (it must work logged-out) — it renders its
own `ThemeToggle` instead.

**`components/Nav.tsx`** (27 lines) — `LINKS` (href/label pairs for the 7 sections); active when
the pathname equals the href or starts with it (so `/notices/3` highlights Notices); brand wordmark
(gradient text via CSS); right side: `ThemeToggle` + Sign out (clears the token, pushes `/login`).
Adding a section = one `LINKS` entry + the page folder.

**`components/ui.tsx`** (27 lines) — four primitives used everywhere: `Card` (optional title +
right-side `action` slot in `.card-head`), `Badge` (`tone`: good/warn/bad/info → CSS class),
`ErrorText` (renders nothing when null; `role="alert"` when shown), `Empty` (muted placeholder
paragraph). Keeping these central means a visual change (e.g. card radius) is a one-file edit.

### 4.3 Data layer

**`lib/api.ts`** (52 lines) — the only fetch code:

| Lines | What and why |
|---|---|
| L1-9 | `BASE` from `NEXT_PUBLIC_API_URL` (build-time public env; default local backend) and the `auth` helper: get/set/clear the token in localStorage (guarded for SSR — `typeof window` check). |
| L11-15 | `ApiError` — an `Error` carrying the HTTP `status`, for pages that care (most just show `.message`). |
| L17-35 | `request<T>`: attaches `Authorization: Bearer …` when a token exists; sets JSON content type for non-FormData bodies; on **401 outside `/auth/`** clears the token and hard-redirects to `/login` (expired session anywhere = back to login, exactly once); on other failures parses the backend's `{detail}` (string or validation array) into the error message; 204 → `undefined`; else parsed JSON as `T`. |
| L37-47 | The verb helpers: `get/post/put/patch/del`, `upload` (FormData passthrough — used for notices, photos, documents), and `blob` (raw fetch for downloads: calendar `.ics`, document files, checklist — returns a `Blob` for `URL.createObjectURL`). |

**`lib/types.ts`** (39 lines) — mirrors of backend responses: `User`, `Check`/`Eligibility`
(verdict union matches the backend's three states), `Readiness`, `ImageSpec`, `Structured` (the
full extracted-facts shape incl. `needs_review` and `method`), `ScamReport`, `Notice`/
`NoticeListItem`, `Answer` (with citations), `DocumentRow` (incl. Phase-2 `is_original`,
`original_id`, `application_id`, `notice_id`, `app_ref`), `IngestJob` (background-job status shape),
`Application`, `Summary`, `PhotoResult` (report checks typed), `Profile` (intentionally loose
`Record` — the form is dynamic), and `DOC_KINDS` (the vault kind list, mirroring the backend).

### 4.4 Pages

**`app/login/page.tsx`** (58 lines) — mode state (`login`/`register`): one form, register adds the
name field; submit posts to `/auth/{mode}`, stores the token, `router.push("/")`. Errors via
`ErrorText`; busy state disables the button. On mount it fetches `GET /auth/providers` and — only
if non-empty — renders "Or continue with Google/GitHub/…" links pointing at the backend's
`/auth/oauth/{p}/start` (full-page redirect flow; the backend's callback stores the token and
bounces home). Header row carries the page's own `ThemeToggle` (no Nav exists here). Note the API
base for OAuth links is read from `NEXT_PUBLIC_API_URL` with the same default as `lib/api.ts` —
keep them in sync.

**`app/page.tsx`** — dashboard (`/`): three parallel loads (`/applications`, `/notices`,
`/applications/summary`). "At a glance" card: open/submitted counts, notices read, documents
ready, heuristic time-saved (formatted `2h 15m`), next deadline; an `.ics` download button
(blob → object URL → synthetic anchor click). Deadlines card: open applications with a tone-coded
days-left badge (`tone()`: passed=bad, ≤7d=warn, else good) and a tracker link. Quick-start card:
the intended first-run path (profile → notice → photo → extension). Recent notices list linking to
detail pages.

**`app/assistant/page.tsx`** — the chatbot; full anatomy in §6. Data: loads `/notices` for the
optional notice picker; each send posts `/assistant/chat {message, notice_id}` and appends a bot
turn carrying the response's agent name + tool badges.

**`app/notices/page.tsx`** (126 lines) — two jobs. **Add:** a file-only submission goes to
`POST /jobs/ingest` (background) and stores a local `IngestJob`; pasted text (or file+text) keeps
the synchronous `POST /notices` and navigates straight to the new notice. A polling effect
(every 1.5s while status is not `ready`/`failed`) refreshes the job; on `ready` it shows the title
+ key-answer summary with a link and reloads the list; on `failed` it shows the backend error.
**Search:** `GET /search?q=` renders result cards (title link, snippet) each with "Save as notice"
(`POST /search/save` → another tracked job). The saved list below is the same list the bot sees —
notices from chat/search/web all land here.

**`app/notices/[id]/page.tsx`** — the richest page. Loads notice + eligibility + readiness in
parallel. Sections: **Key facts** table (last date, age range + as-on, relaxations rendered
`SC +3`, qualification + min %, fee, stages; `needs_review` fields named with a "check against the
original" note; extraction `method` shown for transparency); **Is this notice safe?** (scam badge/
score/reasons/disclaimer); **Am I eligible?** (verdict badge via the `VERDICT` map, per-check
pass/fail/unknown badges + details, profile-completion link listing the missing fields);
**Ready to apply?** (animated readiness bar, missing labels, deep links to photo studio with
`?notice=` preselected and to the vault); **Before you apply** (printable checklist opened as a
blob in a new tab); **Ask this notice** (per-notice chat: question → answer + deduplicated
"From page(s) N" citation line); **Delete** (deletes the notice, applications keep history —
backend nulls their link).

**`app/photo/page.tsx`** (120 lines) — the studio. Inputs: kind (photo/signature), optional notice
(its extracted spec fills the rules; `?notice=` from the detail page preselects it), manual
width/height/min-KB/max-KB overrides, and — for photos — the **background colour** control: preset
select + free-text "any colour name or #hex" + a native colour swatch feeding the same value
(free text wins over the preset; if the notice mandates a background the backend overrides and
warns — the UI prints that warning from the report). The original preview uses an object URL
(revoked on change/unmount). Submit builds FormData (only non-empty overrides are sent, so "from
notice" placeholders stay authoritative) → result panel: processed preview, per-check ok/check
badges with details, warnings in red, and a download anchor using the backend's filename. "Save to
vault" defaults on; the saved row is an application copy (see vault page).

**`app/vault/page.tsx`** (79 lines) — upload form (kind select from `DOC_KINDS` + file) and the
documents table: kind, filename, **"Original" vs "Copy · APP-####"**, size, and actions —
Download (blob), Make application copy (originals only, `POST /documents/{id}/copy`), Delete
(copies delete freely; deleting an original first tries normally and, on the backend's 409, asks
via `confirm()` naming the dependent copies before retrying with `?force=true`). The 5 MB/50 MB
quotas are enforced by the backend; failures surface through `ErrorText`.

**`app/tracker/page.tsx`** (56 lines) — add-application form (title + optional deadline) and the
tracker table: deadline with days-left badge (passed/≤7d colour rules), an inline status `<select>`
that PATCHes on change and reloads, and Remove. Statuses mirror the backend's
`planned/in_progress/submitted/closed`.

**`app/profile/page.tsx`** (71 lines) — the profile form driving autofill + eligibility.
`TEXT_FIELDS` is a data-driven field list (key, label, input type) rendered into a grid; gender and
qualification are selects (qualification values mirror the backend's ordered levels);
`ex_servicemen_ward` is a checkbox. Save strips empty values and coerces the two numeric fields
before `PUT /profile` (empty string would fail backend numeric validation). Below: the Telegram
card — "Create link code" (`POST /bot/link-code`) shows the 10-minute code for `/link CODE`.

## 5. Theme system (dark / light)

```
layout.tsx inline script (pre-paint) ──sets──► <html data-theme="dark|light">
                                                        │
globals.css: :root = light tokens;  :root[data-theme="dark"] = dark tokens
                                                        │
ThemeToggle button ──► applyTheme() ──► dataset.theme + localStorage("applypilot_theme")
```

- **No flash:** the script runs before first paint; `suppressHydrationWarning` on `<html>` covers
  the intentional mismatch.
- **Persistence & default:** explicit choice (localStorage) > OS `prefers-color-scheme` > light.
- **Adding a themed colour:** add one variable to **both** `:root` blocks and use `var(--x)`.
  Never add a raw hex outside the token blocks (badges/bubbles use `color-mix` with tokens so they
  adapt for free).
- The toggle appears in `Nav` (signed-in) and on the login card (signed-out); both use the same
  component and storage key, so the choice is consistent across the login boundary.

## 6. Chatbot interface anatomy

`app/assistant/page.tsx` (125 lines), top→bottom:

- **Welcome turn** seeded in state (bot avatar + what it can do) — the conversation never starts blank.
- **Notice picker** — optional `<select>` (`Any notice` default). Its value is sent as `notice_id`
  with every message; changing it mid-chat re-scopes subsequent answers.
- **Suggestion chips** (7 one-tap questions) — clicking sends immediately; disabled while busy.
- **Transcript** — turns are `{role, text, agent?, blocked?, tools?, ts}`. Rendering: bot rows get
  the gradient `✦` avatar + left-flattened bubble; user rows right-aligned. Under each bot bubble,
  `.msg-meta` shows the timestamp, a guardrail/agent badge, per-tool ok/fail badges (from the
  backend's `tools_used`), and a **Copy** button (`navigator.clipboard`, bot turns after the welcome).
- **Typing indicator** — while `busy`, a bot row with three blinking dots; auto-scroll
  (`scrollIntoView({behavior:"smooth"})`) runs on every turn/busy change.
- **Composer** — Enter submits (form `onSubmit` + explicit Enter handler), **Clear** resets to the
  welcome turn (disabled until the user has spoken or while busy), Send disables on empty/busy and
  reads "Thinking…" while waiting. On success the input refocuses for rapid follow-ups.
- **Failure handling** — a failed request appends an apologetic bot bubble (the conversation
  survives) and also sets `ErrorText`; blocked answers show the "blocked by guardrails" badge
  instead of an agent badge.
- **Footer note** — "answers cite the notice; confirm on the official portal" sets expectations.
- The same backend endpoint powers Telegram/WhatsApp, so questions behave identically in chat apps.

## 9. How to add a new feature (recipes)

**New page:** create `app/<name>/page.tsx` with `"use client"`, wrap the default export in
`AuthGate`, add one entry to `Nav`'s `LINKS`, model data loads on the notices/assistant pattern
(`useEffect` → `api.get<T>` → `useState`, `ErrorText` for failures). Use `Card`/`Badge` from
`components/ui.tsx` — don't invent new card markup.

**New backend field on a screen:** add it to `lib/types.ts` first (mirror the backend schema),
then render. If `tsc` complains elsewhere, that's the point — fix those sites too.

**New themed style:** add tokens to both `:root` blocks in `globals.css`, then classes. Never
inline raw colours in TSX (the two existing inline styles are layout-only: flex row, image height).

**New chat capability:** the UI rarely changes — a new agent/tool on the backend shows up as new
tool badges automatically. A new suggestion = one string in `EXAMPLES`. A new per-turn affordance
(e.g. "regenerate") = extend the `Turn` type + the `.msg-meta` row.

**Forms:** follow photo/profile: controlled inputs in `useState`, build the payload explicitly
(send only meaningful values), disable submit while `busy`, surface errors with `ErrorText`,
confirm destructive actions (`confirm()` as in vault delete) and reload the list after mutations.

**Golden rules:** all fetches via `lib/api.ts`; no secrets in `NEXT_PUBLIC_*`; every new page
behind `AuthGate` except auth-flow pages; keep `suppressHydrationWarning` + the theme script
untouched in `layout.tsx`; run `npm run lint` and `npm run build` before committing (and revert
generated churn in `tsconfig.tsbuildinfo`/`next-env.d.ts` if it appears).

## 10. Known limitations and improvement ideas

1. **No frontend tests.** Add Vitest + Testing Library for `lib/api.ts` (401 handling) and the
   assistant turn rendering when the UI next changes materially; Playwright for the login→chat path.
2. **`NEXT_PUBLIC_API_URL` is build-time.** Local port juggling (3000/3001/3011) caused real
   confusion; a runtime config (e.g. served `/config.json`) or a same-origin `/api` rewrite in
   `next.config.mjs` would remove the whole class.
3. **Token in localStorage** is XSS-readable by design trade-off for this app shape; the hardened
   option is an HttpOnly cookie session (backend change: cookie auth + CSRF), which would also
   retire the OAuth localStorage handoff page.
4. **Assistant history is in-memory** — a refresh loses the chat. Persist turns per notice in
   localStorage (cheap) or server-side (better, needs an endpoint).
5. **No streaming** — answers appear whole after the typing indicator. The backend would need an
   SSE/streaming variant of `/assistant/chat`; the UI seam is `send()` in the assistant page.
6. **Polling for ingest jobs** (1.5s) is fine locally; websockets/SSE would be the hosted upgrade,
   matching a real job queue on the backend.
7. **Accessibility:** bubbles/badges are semantic-lite; add `aria-live` announcements for new bot
   turns (the transcript container is the place) and focus management after Clear.
8. **The login page duplicates the API-base default** for OAuth links — import it from `lib/api.ts`
   instead (export `BASE`) to kill the drift risk noted in §4.4.

## 11. Glossary

- **App Router** — Next's folder-based routing (`app/<segment>/page.tsx` = URL).
- **AuthGate** — the wrapper enforcing "token or /login" + rendering Nav/container.
- **Turn** — one chat message (user or bot) in the assistant's state list.
- **Token (theme)** — a CSS variable (`--brand`, `--card`, …) holding a colour per theme.
- **Standalone output** — Next build mode producing a self-contained `server.js` bundle.
- **Blob download** — fetching binary/file responses and saving via an object URL (calendar, documents, checklist).
